# Changelog

All notable changes to dreamd are documented here.
Format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/).
This project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Security

- **rmcp moves from 1.7.0 to 3.12.0, clearing five advisories.** GHSA-9pj6-vhgr-3mwh (high): an unauthenticated client could grow the Streamable HTTP server's session table without limit, a remote denial of service. It affected only builds with the `mcp-http` feature (`dreamd mcp --bind`); the release binaries and `npx -y dreamd-mcp` are stdio-only. The other four were in rmcp code dreamd never compiles: its OAuth client (GHSA-33f5-2c5q-wgwj, GHSA-c9xm-49cp-xcr9) and its HTTP client (GHSA-9g45-5xwm-f3wc, RUSTSEC-2026-0462). The MCP tools, their names (`search_nodes`, `append_node`) and their results are unchanged. `deny.toml` and `.cargo/audit.toml` no longer ignore RUSTSEC-2026-0462.
- **`url` and `cookie` are updated** (RUSTSEC-2026-0592, RUSTSEC-2026-0594). `url` moves from 2.5.8 to 2.5.9, past a stack overflow in `Url::origin()` on nested `blob:` URLs; `reqwest` and `tower-http` pull it in. `cookie` moves from 0.18.2 to 0.18.3, past private-cookie nonces that can repeat after a fork. It is in the lockfile only behind `ureq`'s cookie support, which no dreamd build enables.

### Fixed

- **In daemon mode, a project whose path ends in a space or tab is refused, and the message names the path** (DRM-161). HTTP drops a trailing space or tab from a header value, so `dreamd mcp`, setup's first lesson and `dreamd dream` sent such a project to the daemon as another folder's path: it got "not registered", or a write meant for `foo ` landed in a registered `foo`. Now all three refuse the project before they send anything that carries `X-Agent-Root`, quoting the path so the space or tab shows. `dreamd mcp` answers `-32600`. `dreamd dream` exits with the error while a daemon answers, and does not run the cycle in-process. With no daemon running, nothing changes.

  Library: new `daemon_client::agent_root_header_refusal`.
- **After `update`, an installed `dreamd service` still starts, and a service whose binary is gone is reported** (DRM-164). `update` removed every cached version but its own, including the one the service's unit, plist or task names, so on Linux systemd failed to start it (203/EXEC) every 5 seconds with nothing saying so; one machine counted 15,841 restarts in about 22 hours. Now `update` keeps the cached version an installed service runs and prints the `service install` and `service restart` commands that move the service to the new version, even under `--quiet`. When the binary a service names is already gone, `update`, `dreamd status` and `dreamd doctor` say so with the same commands, and `doctor` exits 1.
- **The Linux user unit stops restarting after 5 starts in 5 minutes** (DRM-164). It now carries `StartLimitIntervalSec=300` and `StartLimitBurst=5`; with `RestartSec=5`, systemd's default limit never tripped. `service install`, `start` and `restart` run `systemctl --user reset-failed dreamd.service` first, so they work on a unit that hit the limit. Rerun `service install` to get the new unit.

  Library: new `service::InstalledService` and `service::read_installed_service`; `update::UpdateRequest` has a new `service` field.

- **A SIGTERM to `npm exec` for `npx -y dreamd-mcp watch` now stops the native daemon** (DRM-160). npm runs the shim through `sh -c`, and where `/bin/sh` is dash (Debian, Ubuntu) a SIGTERM to `npm exec` killed only that shell. The shim and `dreamd watch` kept running and held the project's writer lock, so `forget`, `archive` and `memory checkout` refused. Now the shim checks every half second whether the process it started under is gone. When it is, the shim sends `dreamd` a SIGTERM, and `watch` stops and removes its socket. Any harness that kills `npm exec` now also stops the server it started. `dreamd mcp` already ended on stdin EOF, so nothing changes for it. Not on Windows.
- **A test's fake daemon no longer panics on macOS when `dreamd mcp`'s reachability probe has already closed its connection** (DRM-165). macOS answers `setsockopt` on such a socket with EINVAL; the fake daemon in `tests/project_root.rs` now skips that connection, as `daemon_client`'s own test does. Every other fake daemon already ignored the error, and the remaining `.expect` calls are on client connections to a live daemon. Tests only.

### Changed

- **`dreamd forget` clears the copies dreamd keeps, and says what it cleared and what remains** (DRM-168). It removed the event from the live log, `LESSONS.md`, the recurrence sidecar and recall, but full copies stayed in every autosnap and memory branch object under `.agent/.dreamd/branches/objects/`, in the decay archive, in `AGENT_LEARNINGS.jsonl.bak`, and in the index's segment files, and `dreamd memory checkout` of an autosnap brought the event back. Now one redo WAL commits the live files together with:
  - each branch object that holds the event, written again without it. Every ref, and a detached `HEAD`, that named the old object moves to the new one and keeps its name and timestamp. The old object is deleted after the commit. An object that fails its hash check is left as it is and reported;
  - the event's line removed from the decay archive and the migrate backup. An event that decay had already archived is now removed there too: `removed=false` with `cleared: decay_archive`, where it used to change nothing.

  After the index refresh, it merges every segment that holds a deleted document, so the event's text leaves the segment files. Before, the text stayed there until a merge or `dreamd doctor --repair`.
- **`dreamd forget` reports git history and never rewrites it.** When committed `.agent/` files hold the event, it prints how many commits, the first and last, and a `git filter-repo` command you can run yourself, with a warning that clones, forks and remotes keep their copies until each one rewrites too.
- **`dreamd forget` prints more lines.** Line 1 is unchanged. Then stdout has `cleared: <places>`, and one `remaining: <place> …` line per place a copy is still kept. `--dry-run` prints `would_clear:`, one `would_touch:` line per file, object or ref it would change, and `remaining:`. A script that compared the whole stdout to one line should read the first line. The git note goes to stderr.
- **The forget receipt is `forget-receipt/1.1`.** It keeps every 1.0 key, in order and with its meaning, and adds `cleared` and `remaining`. `removed` is `false` when only copies held the event. It holds ids, commit ids, relative paths and counts, never content, and it is still unsigned.

  Library: new `copies` module (`find`, `git_history`, `rewrite_command`) and `server::{compact_deletes, Compaction}`. New `forget::{Place, Remaining, ForgetOutcome, IndexOutcome}` and `ForgetError::{Copies, Branches}`. `ForgetReport` gains `cleared`, `copies` and `left` and is no longer `Copy`. `render_receipt` takes the report and a `ForgetOutcome`.

## [1.4.0] - 2026-11-20

A minor release that hardens what 1.3.2 shipped. Recall takes any text, returns one stable order and refuses a `k` above 100. Each project is redacted and configured by its own config, and an API key goes only to its own vendor. A dream cycle keeps a hand-edited `LESSONS.md`, promotes a key only on its own events, and commits only on a branch. Every client call to the daemon has a deadline and checks the daemon's version before it sends anything. `dreamd setup` keeps a repo's `AGENTS.md` loaded in Claude Code. Recall is still BM25 × salience. The record schema (`1.0.0`) and the index schema (`index/1.3`) are unchanged, so no store migration or index rebuild is needed. Several changes are visible to scripts and agents; they are listed under "Upgrading from 1.3.2".

**Upgrading from 1.3.2.**

- **Restart the daemon.** A 1.4.0 client asks the daemon its version before its first call and refuses a daemon of another version before anything is sent. Run `npx -y dreamd-mcp update`, which stops the `dreamd mcp` and `dreamd watch` processes under your home and removes the other cached binaries. Then run `npx -y dreamd-mcp watch` and reload your MCP harness. If a `dreamd service` unit runs the daemon, run `npx -y dreamd-mcp service install` (add `--force` on macOS) and `npx -y dreamd-mcp service restart` in place of `watch`. With a cargo-installed `dreamd`, stop the old daemon and run `dreamd watch`.
- **Commit `.agent/`.** `dreamd doctor` fails with `memory_in_git` (exit 1) while the episodic log is not tracked by git (DRM-100). A dream cycle keeps a hand-edited `LESSONS.md` and makes no model call. A `LESSONS.md` that differs from HEAD while the store has no baseline yet (uncommitted output of an older cycle, or a fresh clone) is kept until one `git commit` of it; after that, cycles write lessons again (DRM-115).
- **The daemon home is not a store.** A store in `~/.agent/` fails `doctor` and shows in `status` as `daemon_home_store:`. `init` and `setup` exit 2 in `$HOME`, and `uninstall --purge` refuses while `~/.agent/` holds a store. A `dreamd mcp` with no store at or above its folder answers `-32600` "this folder is not set up for dreamd" from both tools (DRM-101). `dreamd mcp --project-root` must name a folder that holds `.agent/`, or it exits 2 (DRM-102). In a fresh clone or worktree, run `dreamd init` once (DRM-107).
- **Recall.** A query is plain text: quotes, `field:`, `AND`/`OR`, `+`/`-` and `*` are words now, not operators (DRM-108). `k` is at most 100 on every surface: a larger value gets `k must be at most 100` (MCP `-32602`, HTTP `400`, CLI exit 2) (DRM-109). Results with equal scores come back in event-id order (DRM-110).
- **Appends.** A `client_dedup_key` matches only a retry of the same learning; the same key with different content is stored as a new record (DRM-106). A bad append gets the same code and message in daemon and in-process mode (DRM-104). A call to a daemon that never answers fails after 30 s, or after `DREAMD_CLIENT_TIMEOUT` seconds; a proxied dream cycle that the daemon has started may take up to 120 s. A timed-out append may have been written, so retry it with the same `client_dedup_key` (DRM-121).
- **Dream cycles.** A key promotes only on events no deeper key has claimed, and a root such as `rust` counts only events filed as exactly `rust`, so a store may get a different `LESSONS.md` and different pins at its next cycle (DRM-117). Each API key goes only to its own vendor: `ANTHROPIC_API_KEY` for Anthropic models and `OPENAI_API_KEY` for OpenAI models. A setup with only the other vendor's key now gets the deterministic lesson (DRM-113). The cycle makes no git commit on a detached HEAD or while a merge, rebase, `git am`, cherry-pick, revert or bisect is in progress (DRM-116). `dreamd forget` unlinks a model-written lesson whose cluster holds the forgotten event, and prints `lesson=unlinked` (DRM-114).
- **Doctor, status and logs.** `doctor` reports `index_freshness: stale content` and exits 1 after a hand edit of a log line's content, `skill_action`, timestamp or scores; stop dreamd's writer and run `dreamd doctor --repair` (DRM-118). `dreamd status` may print `daemon: not responding`, with exit 1 (DRM-121). The daemon log is mode `0600`, appended to, and renamed to `dreamd.log.1` at 8 MiB; a daemon on a non-default `DREAMD_SOCK` logs to `<socket>.log` (DRM-119).
- **The npm shim.** It passes SIGINT, SIGTERM and SIGHUP to `dreamd` and exits with its status, or dies of the same signal. A binary that cannot start exits 1 (DRM-123). `dreamd update` keeps the cached binary of the version it runs and makes no network call; re-run floating `npx -y dreamd-mcp` to get the newest release (DRM-152).
- **Setup and HTTP.** In a repo with an `AGENTS.md`, `dreamd setup` writes the dreamd block to `AGENTS.md` and makes `CLAUDE.md` import it with `@AGENTS.md` (DRM-153). `GET /api/v1/preferences` serves only a regular file inside `.agent/personal/`; a symlink that leads elsewhere, a FIFO or a device gets `500` (DRM-120).

### Security

- **The daemon redacts each project by that project's own config** (DRM-103). It used the `redaction` setting of the project `dreamd watch` started in for every project it served. A project with `redaction = true` could store a secret raw when the daemon was started in a project with it off. Now each project's own config applies, read on every append, so an edit takes effect on the next append without a restart.
- **Redaction catches the secret shapes it documents, and replaces only the value** (DRM-105). It missed several documented shapes and kept parts of some secrets: OpenAI `sk-proj-` keys, the base64 tail of a bearer token, a quoted password after its first space, `ASIA` keys, and lowercase, JSON and YAML assignments. It now catches the 14 shapes listed in `docs/configuration.md`, and replaces only the value of an assignment, a bearer token or a URL password, so the name and any quotes stay. Ordinary words such as `Bearer authentication` and numeric settings such as `MAX_TOKEN=4096` are no longer replaced. Records stored before are unchanged: `dreamd doctor` lists those that match under `stored_secrets:`, by line and event id, for `dreamd forget <id>`. `SECURITY.md` and `docs/configuration.md` now say that `DREAMD_LOG=debug` logs MCP requests in full, before redaction.

  Library: new `redaction::would_redact`.
- **Each LLM API key is sent only to its own vendor** (DRM-113). The dream cycle sent the first key it found to whichever vendor the model went to. With only `OPENAI_API_KEY` set, the default `claude-haiku-4-5` sent the OpenAI key to Anthropic. With `model = "gpt-4o-mini"` and both keys set, the Anthropic key went to OpenAI. Now the key is chosen by the vendor the model goes to: Anthropic gets `ANTHROPIC_API_KEY` or `anthropic_api_key`, and OpenAI gets `OPENAI_API_KEY` or `openai_api_key`. An `endpoint` override does not change that. With no key for the vendor, or a model for any other adapter, no model call is made, and `dreamd dream` says which variable and `secrets.toml` key it looked for. A `dreamd dream` proxied to the daemon says that the daemon has no key, and that a key in your shell is not used.

  Library: `llm::resolve_llm_credentials` takes the `Config` and returns `Result<ResolvedKey, NoKey>`, and `dream_cycle::cycle_notices` takes an `Option<&NoKey>` and a `KeyHolder`. New `llm::{NoKey, no_key_for}`, `KeyProvider::{env_var, secrets_key, vendor}` and `dream_cycle::{KeyHolder, no_key_notice}`. `dream_cycle::NO_API_KEY_NOTICE` is removed.
- **`GET /api/v1/preferences` serves only a regular file inside `.agent/personal/`** (DRM-120). The route followed a `PREFERENCES.md` symlink anywhere, so a repo could point it at a file outside the store and an agent would be handed that file. It now serves only a regular file inside `.agent/personal/`, as the dream cycle already did. A symlink within `personal/` still works.
- **The bundled zlib is updated** (RUSTSEC-2026-0544). `libz-sys`, which builds the zlib that libgit2 links for the dream cycle's git calls, moves from 1.1.31 to 1.1.33, past a heap buffer overflow in zlib's `gz_vacate()`.

### Added

- **Property tests drive recall and learn at the edge, in both modes** (DRM-124). They send arbitrary queries, `k` values, project roots and header bytes through in-process mode and through a daemon on a real socket, and check that every query answers, no `k` aborts, a smaller `k` returns a prefix of a larger one, a learning lands in the root it names, no header gets a 5xx, and the two modes store or refuse a learning alike. The nightly job runs them at 256 cases. One exception is known and not fixed in this release: in daemon mode, a project whose path ends in a space or a tab reaches the daemon without that character, because HTTP strips it from `X-Agent-Root`. Such a project gets "not registered", or its writes land in a registered project of the same path without the space (DRM-161).

### Changed

- **The public docs lead with install, and they stop teaching `dreamd memory` as the way to branch.** README's install and quick start now come before the audit essay, and the opening names shared memory and the audit loop together. The npm install note says which platforms have a prebuilt binary. `llms.txt` and `llms-full.txt` match that pitch, and `llms-full.txt` no longer says `recall`, `score`, `status`, `archive`, and `migrate` need a separate binary (the shim has forwarded them since 1.2.1). GUIDE's walkthrough branches `.agent/` with git. `SKILL.md` says the dream cycle runs only when invoked. The npm package description, the MCP registry description, and the Claude plugin description name both jobs. The memory-branch pages stay, marked deprecated. `docs/compared.md`'s dreamd column is re-checked for 1.3.2; its star counts stay dated 2026-07-14.
- **A dream cycle promotes a key on its own events, and a language root no longer collects one-offs** (DRM-117). A parent key promoted on events its children had already claimed, and a language root such as `rust` collected unrelated one-offs, so a single high-pain one-off could become the cycle's only lesson. A key now promotes on at least 3 of its unclaimed events in 30 days, and a one-segment key counts only events filed under exactly that key. Ties between clusters go to more events, then the newest event, then the key ascending, not to the alphabetically last key. The 7-day window never changed a result and is gone from the docs. A store where a parent promoted on its children's events gets a different lesson at its next cycle.

  Library: `consolidation::WINDOW_7_DAYS_SEC` is deprecated and read by nothing.
- **`dreamd mcp` on a terminal says it is waiting for a harness** (DRM-151). When stdin is a terminal, `dreamd mcp` and `npx -y dreamd-mcp` now print one line to stderr: the server is on stdio, waiting for a harness, and the `setup` command connects one (`dreamd setup`, or `npx -y dreamd-mcp setup` under the shim). A harness's piped stdin sees no change, and stdout stays JSON-RPC only.

### Fixed

- **On native Windows, `npx -y dreamd-mcp` no longer says the dream cycle and the Tantivy index are Unix-only.** They run in a `dreamd.exe` built from source or taken from a release `windows-x86_64.tar.gz`. The shim still exits 1 and names WSL2 for the npx path. Prebuilt npm binaries stay Linux x86_64 and macOS.
- **`git clean -fd` can no longer turn into deleted memory unnoticed** (DRM-100). `.agent/` is meant to be committed, but nothing said so, so the episodic log stayed untracked and `git clean -fd` deleted it. The index still held the events. Doctor called that ordinary drift and advised `dreamd doctor --repair`, which rebuilt the index from the empty log and deleted the last copy. Now:
  - while git has no commit of the episodic log, `dreamd setup`'s card prints the command that commits `.agent/` and `.gitignore`, and README's quick start shows it;
  - `dreamd doctor` and `dreamd status` print `memory_in_git:`. Doctor warns, and fails the run, while git has no commit of a log that holds events. A repo that ignores `.agent/` is reported as `ignored`;
  - doctor warns when the episodic log is missing, or holds no record, while the index holds events, and says to stop dreamd's writers and restore the file. It no longer advises `--repair` then;
  - `dreamd doctor --repair` refuses in that case, and `--allow-empty-log` rebuilds anyway.

  Library: new `autobiography::{log_git_state, LogGitState, commit_store_command}`.
- **The daemon home is never a project store** (DRM-101). `~/.agent/` holds dreamd's registry, socket and log, but the walk up from a folder took the first `.agent/` it found. So every folder under your home with no store of its own bound to your home directory: an in-process `append_node` wrote `~/.agent/episodic/`, a literal `--project-root "~/x"` started in your home did the same, and `dreamd init` or `setup` in a git repo at your home directory registered the daemon home as a project. Now:
  - the walk skips an ancestor whose `.agent/` is the daemon home, comparing real directories, so a folder under your home with no store finds none;
  - `dreamd init` and `dreamd setup` exit 2 and write nothing when the project root's `.agent/` would be the daemon home. `init --uninstall-project` still runs there, so an old `$HOME` entry can be removed;
  - `dreamd mcp` in a folder with no store answers `search_nodes` and `append_node` alike with `-32600`: the folder is not set up, run `dreamd setup` (or `npx -y dreamd-mcp setup`) in the project folder and restart the MCP server. It writes nothing, and in daemon mode it no longer calls the daemon with the working directory as `X-Agent-Root`. This replaces `coordinator unavailable: no agent root found` and the empty `{"results":[]}`;
  - `dreamd doctor` and `dreamd status` print `daemon_home_store:` while `~/.agent/` holds a project store, with the event count and how to move it (or, with no events, what to remove). Doctor fails its run on it, and prints the line on stderr when it finds no store at all. `docs/troubleshooting.md` has the steps;
  - `dreamd service uninstall --purge` refuses, before its prompt and with `--yes`, while the daemon home holds a project store or is a registered project's store.

  A `dreamd service` unit installed from a folder whose only store was the daemon home ran `watch` on it. That `watch` now finds no store and exits 2; reinstall the service from the project.

  Library: new `layout::same_dir`, `AgentRoot::discover_with`, `DaemonHome::{stray_episodic_dir, stray_episodic_jsonl}`, `memory_store::{NotSetUpStore, not_set_up_message}` and `MemoryMcpServer::not_set_up`.
- **The project path the MCP server sends is absolute UTF-8, and `--project-root` must name a store folder** (DRM-102). Three fixes:
  - the daemon refuses a relative or empty `X-Agent-Root` with `400`, instead of resolving it against its own working directory, where it could reach the daemon's own project. A missing header and one that is not UTF-8 are `400` too, and each message says to send the absolute path of the folder that holds `.agent/`. In daemon mode, `dreamd mcp` answers these with `-32600`;
  - a project whose path has non-ASCII letters, such as `é`, works in daemon mode. The daemon read `X-Agent-Root` as ASCII only, so `search_nodes`, `append_node` and `dreamd dream` failed there with `missing or non-UTF-8 X-Agent-Root header`. The header is the path's UTF-8 text, sent as raw bytes;
  - `dreamd mcp --project-root` must name a folder that holds `.agent/` itself, and not the daemon home. A relative path is resolved against the working directory, and a leading `~` is not expanded. Otherwise `dreamd mcp` exits 2 and says why, in daemon and in-process mode alike.
- **`doctor`, `dream` and `mcp` read the project's config from any folder inside it** (DRM-103). They read the config of the working directory itself, so from `<project>/src` they got the user-level config, and a `dream_cycle_mode` or a malformed file in the project went unseen. Now they find the store first and read its config. With no store, `doctor` and `dream` exit 2 before reading any config. A project config that fails to load answers an append with `-32600` `config load failed: …` in both modes; in-process `dreamd mcp` answered `-32603`, and the daemon wrote the event with the other project's settings. Over HTTP the learn is `500`.
- **An append is checked once, by one function, in the process that owns the store** (DRM-104). In-process `dreamd mcp` ran the ingress checks itself, but in daemon mode the client checked `pain` and `importance` before the daemon checked `skill_action`, so a call with a bad `skill_action` and a bad score named the score in one mode and the `skill_action` in the other. Now the daemon runs the one check on arrival, and in-process and daemon mode answer every bad append with the same code and message. HTTP no longer reads `pain` and `importance` into a 32-bit float before it checks them, so `10.0000001` is refused instead of stored as `10.0`. The record still stores the nearest 32-bit float.
- **A dedup key no longer drops a different learning** (DRM-106). A second `append_node` or `POST /api/v1/learn` with the same `client_dedup_key` and different content answered `deduplicated: true` with the first id, and the new content was never stored. The MCP instructions told agents to use one key per topic, such as `session:YYYY-MM-DD:skill.topic`, so a correction sent with that key was lost. A key now matches only a retry of the same learning (the same content, `skill_action`, `source_harness`, scores and `pinned`); the same key with different content is stored as a new record with its own id. The MCP instructions, `AGENTS.md.snippet`, `SKILL.md` and the HTTP docs say to use the key only to retry one write, and that keys are forgotten when the server restarts. Daemon-mode MCP now sends the key in the request body, so a non-ASCII key or one with a newline works there as it does in process: the daemon dropped a non-ASCII `X-Client-Dedup-Key` header, and a key with a newline failed to send. `POST /api/v1/learn` takes the key as a `client_dedup_key` body field or as the header, and answers `400` when the header is not UTF-8 or when the two differ.
- **A clone or a worktree is refused with its folder and the command, and `init` repairs it** (DRM-107). With a daemon running, every MCP call in a fresh clone or `git worktree` answered `project not registered with daemon; run dreamd init`, and nothing said why: the daemon serves only registered stores, and a clone is a new path. The error now names the store's folder and the exact command, `dreamd init` or `npx -y dreamd-mcp init` under the npm shim, and says the next call works without a restart. `init` on an existing store now re-creates the folders git does not keep (`semantic/`, `personal/` and the ignored `.dreamd/`, in a clone), so `dreamd doctor` no longer warns `missing_subdir` in every clone. It creates no file, and a scaffold path that is a file is an error. GUIDE §9 covers what is shared through git, what each checkout keeps, and how to merge two checkouts' logs.
- **Recall takes any text** (DRM-108). `search_nodes`, `GET /api/v1/recall`, `dreamd recall` and `dreamd blame` parsed the query with Tantivy's query grammar, so most ordinary requests failed with `-32602` or `400`, including setup's own suggested test sentence. All four now take any text: dreamd splits it into words, and a piece that splits into several words, such as `parse_config()`, matches as a phrase. A plain-word query scores exactly as before. Quotes, `field:`, `AND`/`OR`, `+`/`-` and `*` are words now, not operators.
- **Recall's `k` has a maximum, and no recall allocates for more documents than the index holds** (DRM-109). `k` had no limit and sized an allocation up front, so `GET /api/v1/recall?k=4294967295`, or `search_nodes` with `"k": 4294967295`, aborted the daemon or `dreamd mcp`. `k` is now at most 100 on every surface: HTTP `k`, MCP `k`, and `-k` on `dreamd recall` and `dreamd blame`. A larger value is refused with `k must be at most 100`: HTTP `400`, MCP `-32602` in both modes, and exit 2 on the CLI. `k = 0` still returns no results. The `k` schema of `search_nodes` now shows its default, 5, and its maximum, instead of a rustdoc link.

  Library: new `ingress::{MAX_RECALL_K, k_too_large_message}`.
- **Recall results have one order: score, then event id** (DRM-110). Two results with the same score came back in an order that depended on the index's segments and on `k`, so `-k 1` and `-k 4` could disagree on the top hit. An event and the lesson built from it often score the same. Results are now ordered by score, then event id, on every path. An event comes before a lesson with the same score.

  Library: a `SalienceCollector` fruit now also holds the documents that tie its `k`-th, so it can hold more than `k`. `recall` and `score_by_salience` still return at most `k`.
- **Decay no longer archives a pinned event that has an unpinned copy** (DRM-157). The log can hold two lines with one id, one pinned and one not, as a merge of two clones that keeps both sides leaves. - **A setup that refuses an MCP config writes nothing** (DRM-158). When `dreamd setup` refused a conflicting or malformed `.mcp.json` or `.cursor/mcp.json`, it said "nothing was written" after it had already made `.agent/`, appended `.gitignore` and registered the project. Pins on the lesson's other citations stay, and older copies of `LESSONS.md` stay in the autosnap objects until retention prunes them.
- **A dream cycle keeps a hand-edited `LESSONS.md`** (DRM-115). A cycle saw that `LESSONS.md` held a hand edit, overwrote it anyway, then said to commit the edit it had erased, in the CLI and in `POST /api/v1/dream`. Now the cycle keeps the file, makes no model call, and says so (`lesson kept: …`, and `lesson_held` in the `/dream` body). It writes the lesson again once the edit is committed with git or the file is deleted. The same holds in a fresh clone, or in a store with no baseline yet, where the file differs from HEAD. Pins and decay still change the log.
- **`dreamd doctor` notices a hand edit of a log line's content or scores** (DRM-118). After a hand edit of a line's `content`, `skill_action`, timestamp, `pain` or `importance`, recall kept the old text and score, and `dreamd doctor` still printed `index_freshness: ok`: it compared only which ids the log and the index hold. Formatting and fields recall does not read, such as `source_harness`, `pinned` and `x_` fields, do not count. - **A `dreamd watch` that fails to start leaves the running daemon's log alone** (DRM-119). The error names the socket, and a client never falls back to in-process beside that daemon. A timed-out `append_node` says it may have been written and to retry with the same `client_dedup_key`. `dreamd status` sends one request with a 2 s deadline and reports `daemon: not responding` (exit 1) when it gets no answer.

It deleted every cached binary under `~/.cache/dreamd-mcp`, the running version's included, and said the next spawn fetches the new binary, when no newer release might exist. It now keeps the running version's binary, removes the other versions, and says that the next floating `npx -y dreamd-mcp` runs whatever version npx resolves; the shim downloads a binary only for a version it has not cached. `update` still makes no network call. A SIGTERM or SIGINT sent to the shim of `npx -y dreamd-mcp watch` stopped the shim and left the native daemon running, so `forget`, `archive` and `memory checkout` then refused while it held the project's writer lock. A `dreamd` killed by a signal, or a binary that could not start, made the shim exit 0. The shim now passes SIGINT, SIGTERM and SIGHUP on to `dreamd`, waits for it, and exits with its exit code, or dies of the same signal. A binary that cannot start exits 1 and names its path. A signal sent to the `npm exec` process itself still does not reach the shim where `/bin/sh` is dash, as on Debian and Ubuntu: npm runs the shim through `sh -c`, a SIGTERM stops only that shell, and npm ignores SIGINT. Send the signal to the process group, or press Ctrl-C in the terminal.
- **The dream cycle's git commit skips a detached HEAD and a git operation in progress** (DRM-116). The cycle committed on a detached HEAD, so `git checkout` back to the branch dropped the cycle's learnings, lesson and pins from the live store. It also committed with one parent in the middle of a merge. Now the commit is skipped while HEAD is detached or a merge, rebase, `git am`, cherry-pick, revert or bisect is in progress, with a reason that says what to finish (`detached_head`, `merge_in_progress` …). The cycle still runs, and the next cycle on a branch commits.

Claude Code loads `AGENTS.md` only while the folder has no `CLAUDE.md`, so the `CLAUDE.md` setup created for its dreamd block made Claude Code stop loading a repo's `AGENTS.md`, and nothing said so. A `CLAUDE.md` that already imports `AGENTS.md` keeps every byte except its dreamd block, and one that is empty or holds nothing but a dreamd block, as setup wrote it before, becomes `@AGENTS.md`. Any other `CLAUDE.md` keeps its block, `AGENTS.md` is not touched, and the card says to add a line `@AGENTS.md` to `CLAUDE.md`. Without an `AGENTS.md`, setup writes the block into `CLAUDE.md` as before. The `AGENTS.md` block asks for `source_harness` set to the name of the tool the agent runs in.
- **`--harness none` and the Cline guide name the project root, and the MCP instructions name no HTTP call** (LP-INSTALL-09, LP-MCP-12). The MCP block that `dreamd setup --harness none` prints, and the Cline guide's configs, now pass `--project-root` with the project's absolute path: a global MCP config starts the server outside the project, where it answered "not set up". The MCP server instructions and `adapters/claude-code/AGENTS.md.snippet` no longer tell agents to call `GET /api/v1/preferences`, which no MCP tool reaches. The snippet's search line is now the same rule as the instructions: the user's request as the query, and any text works.
- **A client checks the daemon's version before its first call** (DRM-122). Against a daemon from 1.2.2 or earlier, which sends no version, `append_node` wrote the learning and then reported a version mismatch, so each retry stored a duplicate, and `dreamd dream` ran the cycle and then failed. `dreamd mcp` and the `dreamd dream` proxy now send `GET /api/v1/health` once per process before their first call, and send nothing more on a mismatch. When the client is the older side, the message says so and says to update it, or to remove an npx pin (`dreamd-mcp@<version>`) from the MCP config, instead of restarting the daemon. The daemon's own `426` body follows the same rule.
  Library: new `daemon_client::{preflight_version, preflight_version_tcp}`.
- **On macOS, `dreamd watch` refuses a regular file at the socket path with its own message.** A regular file refuses the connect probe with `ENOTSOCK` on macOS, not `ECONNREFUSED`, so `watch` failed with `Socket operation on non-socket` instead of `… is not a unix socket; refusing to unlink it`. The file was never removed. The probe now checks the file type first, on every platform.

On Windows `install` writes a Task Scheduler 1.2 XML to `%USERPROFILE%\AppData\Roaming\dreamd\dev.dreamd.dreamd.xml` — a `LogonTrigger` task named `dev.dreamd.dreamd`, `InteractiveToken` / `LeastPrivilege` (never `HighestAvailable`), `RestartOnFailure` every `PT1M` up to three times as the analogue of `Restart=on-failure` / `KeepAlive`, whose `Actions/Exec` is this binary plus `watch` with `WorkingDirectory` = the `AgentRoot` project root discovered from cwd at install time — and registers it with `schtasks /Create /TN dev.dreamd.dreamd /XML <path>`. That is a scheduled task, not a Windows Service: no `sc.exe`, no SCM, no `CreateProcess` detach, no PID file, no heartbeat. - **`dreamd service uninstall` — remove the user-scope service (AILAB-202).** The fifth verb on the nested `dreamd service` command, and the inverse of `install` — only of `install`. On Linux it runs `systemctl --user disable --now dreamd.service`, unlinks `~/.config/systemd/user/dreamd.service` in-process (systemd has no verb for that), then `systemctl --user daemon-reload`; on macOS a best-effort `launchctl bootout gui/<uid>/dev.dreamd.dreamd` followed by unlinking the plist. Unlike `start` it is **idempotent**: a unit or plist that is already gone is not a failure, and on Linux an absent unit file means `systemctl` is never spawned at all. Stdout is a locked removed/preserved block — `removed: <path or (none)>`, `preserved: <daemon home>`, and an unconditional `preserved: per-project .agent/ stores`, because **no flag on this verb deletes a project's memory** and that promise is worth printing. `--purge` widens the blast radius to exactly one directory, the daemon home `~/.agent/` (registry, socket, `dreamd.log`); it never walks a per-project `<repo>/.agent/` store — that wipe is still the manual “Full fresh store” in [troubleshooting.md](docs/troubleshooting.md) — and never touches `~/.config/dreamd/`. Being destructive, `--purge` borrows the `reset workspace` confirmation idiom wholesale: `--yes`, or a typed `y` / `Y` on a tty, with non-tty stdin refused (exit 2) rather than silently obeyed in a pipeline; `--yes` on its own, without `--purge`, is accepted and ignored the way `--force` is on a Linux install. The confirmation runs **before** any mutation, so a refusal or a declined prompt leaves the unit installed and the supervisor unspawned. A host with no backend is the existing `ServiceError::NoSystemd` (exit 2) and is refused before it can prompt — there is no unit to take away. This is **not** the top-level `dreamd uninstall` (AILAB-226), which stops local `mcp` / `watch` processes, drops the socket and clears caches while leaving the service entry in place: the two verbs are deliberately separate, and `service uninstall` never touches a process table — on a supervised host `disable --now` / `bootout` *is* how the daemon stops. The tty probe and the confirmation read are injected alongside the `systemctl` / `launchctl` runners and the uid, so no unit test blocks on real stdin or reaches a live supervisor, and the macOS path is exercised on Linux CI.

- **`dreamd service install` / `dreamd service start` — macOS LaunchAgent (AILAB-169).** On macOS `install` writes `~/Library/LaunchAgents/dev.dreamd.dreamd.plist` (Label `dev.dreamd.dreamd`, `ProgramArguments` = `<this binary> watch`, `WorkingDirectory=<project root discovered from cwd at install time>`, `RunAtLoad` true, `KeepAlive` with `SuccessfulExit=false` — the launchd analogue of `Restart=on-failure`) and loads it with `launchctl bootstrap gui/<uid> <plist>`; `start` runs `launchctl kickstart -k gui/<uid>/dev.dreamd.dreamd`. `--force` is the overwrite confirmation and the only one — no interactive prompt, so non-tty and `npx` invocations behave the same: without it an existing plist is left untouched and `install` exits 2 naming the path and the flag; with it `install` rewrites the plist, runs `launchctl bootout gui/<uid>/dev.dreamd.dreamd` (errors ignored — the agent may not be loaded) and then `bootstrap`. - **Every UDS HTTP request now emits one INFO line carrying peer UID, request id, method, path, status, and latency.** `build_router` mounts `tower_http::trace::TraceLayer` with a hand-rolled `MakeSpan` and `OnResponse`, because both defaults are silent at the level dreamd actually ships. `DefaultMakeSpan` opens at **DEBUG** while `DREAMD_LOG` defaults to `info`, so a stock `TraceLayer::new_for_http()` would have mounted a layer that logs nothing in every default install; `http_make_span` opens `info_span!("http", …)` instead, reading `peer_uid` off the `PeerUid` extension `serve_uds` injects at connection-accept time and `request_id` off `x-request-id`. Raising the span to INFO is necessary but **not sufficient**, which is the part worth knowing: `observability::init_tracing` builds its layers with `fmt::layer()`, whose `with_span_events` default is `FmtSpan::NONE`, so the subscriber writes a line for an *event* and never for a span on its own — a span only reaches the log by decorating an event inside it, and the sole other event on this path is `TraceLayer`'s DEBUG `on_request`. An INFO span correct in every field would therefore have produced zero output under the shipping default. `http_on_response` closes that: it records `status_code` and `latency_ms` onto the span (declared `Empty` at open) and then emits one `info!(parent: span, "http request")`, so every field rides on the span and a request costs exactly **one** INFO line (a 5xx draws `DefaultOnFailure`'s ERROR `response failed` line on top, which is left at its default deliberately). `latency_ms` is f64 milliseconds rather than `Duration::as_millis()`: the warm path is P50 0.30 ms / P99 0.34 ms per `PERF.md`, so an integer field would have read `latency_ms=0` on essentially every request — an AC field that logs without informing. `DefaultOnResponse::new().level(Level::INFO)` was rejected for restating `status` and `latency` as its own event fields under different names, and `on_request` keeps its DEBUG default so `DREAMD_LOG=debug` still gets an arrival line that `info` does not. Request ids are minted by `SetRequestIdLayer` + `MakeRequestUuid` — tower-http's own optional `uuid`, deliberately preferred over a direct `uuid` dep in `dreamd-core` for one call site — and `PropagateRequestIdLayer` copies the id onto the response, which is both a useful correlation header and the seam that lets a test assert the generator ran without a capturing subscriber. Layer order is load-bearing and reads inverted from the `ServiceBuilder` idiom, because axum's **last** `.layer()` is the outermost: `SetRequestIdLayer` sits outside both `PropagateRequestIdLayer` and `TraceLayer`, since each of those reads the header off the request it is handed and either one placed outside the generator records nothing — no compile error, just an empty `request_id` and a response with no header. `peer_uid_middleware` stays outermost of all: auth runs before tracing, so a rejected peer gets no `http` span, which remains the existing `UID mismatch -- 403` `warn!` line's job. Lines reach `~/.agent/dreamd.log` only under `dreamd watch` (AILAB-184 made the file layer daemon-only), where `dreamd status` already tails them. Internal coordinator events stay at DEBUG, `init_tracing` and the `DREAMD_LOG` default are untouched, and stdio MCP gets no layer — this is `build_router` / UDS HTTP only. `tower-http` becomes a direct dependency at the `0.6.11` already in the lockfile as a reqwest transitive, `default-features = false` with only `trace` + `request-id`; the stripped release binary moves 20,030,848 → 20,111,104 bytes against the unchanged 20 MB NFR-2 gate. - **Opening a secondary project's Tantivy index no longer holds the `index_map` mutex.** `AppState::with_index_handle` took the map lock and then called `map.get_or_open(root, |r| TantivyIndexHandle::open(..))`, so the open — a full JSONL replay, a Tantivy commit, and a 50 MB `IndexWriter` allocation — ran inside the guard. Every other project's recall, learn, and dream stalled behind it, because `index_map` is one lock for all non-primary roots. The lock could not simply be narrowed in place: `get_or_open` returns `&mut H` **borrowed from the map**, so the borrow is live for as long as the caller uses the handle and the open must happen while it is held. The map API is therefore split into halves that can straddle a lock release — `ProjectIndexMap::get_handle` (lookup only, marks MRU, `None` on a miss) and `insert_or_adopt` (publish an already-opened handle) — and `with_index_handle` now runs lookup → **release** → open → re-lock → publish, with the open the only statement between the two guards. `get_or_open` is retained unchanged for its three existing callers; both new methods share one `promote` helper with it so the hit-path LRU bookkeeping cannot drift. Releasing the lock makes two first-touches of the *same* root race, and `insert_or_adopt` settles that: **the incumbent wins** — by the time a handle is in the map it may already have handed its `IndexReader` or indexer `Sender` to live requests, and `supervisor_map` caches per-root coordinators wired to that very channel, so replacing it would strand all of them — and the loser is **closed**, not dropped silently, since two live handles on one index directory means two `IndexWriter`s. The losing *open* can also fail outright rather than produce a handle, because Tantivy's per-directory writer lock is non-blocking; that arm re-checks the map before surfacing the error, preserving the old shape's outcome (block, then find the winner's handle) instead of turning a rare race into a 500. `spawn_blocking` was deliberately **not** used: the AC is about the mutex and cross-project blocking, both of which the restructure achieves on its own — the daemon runs a multi-thread runtime, so other workers keep serving while one blocks in the open — and wrapping it would make `with_index_handle` `async` and ripple through every caller for no additional guarantee. The pinned-primary fast path, `TantivyIndexHandle::open` itself, and the eviction policy are untouched. ## [0.1.0] - 2026-08-05

### Changed

- **CLI arms that open the Tantivy index no longer hoist a `stdout` / `stderr` lock.** A hoisted `StdoutLock` / `StderrLock` is process-wide, so a command holding one across an index open could deadlock against Tantivy's own logging threads — the root cause behind the `doctor --repair` hang (AILAB-575). `recall`, `score`, and `setup` now write through unlocked `std::io::stdout()` / `stderr()` handles, which lock and release per `writeln!`. The eight arms that still hoist — `archive`, `init`, `migrate`, `reset workspace`, `status`, `uninstall`, `update`, `version` — each carry an inline `// lock-ok (AILAB-583):` rationale naming why they never open an index, and `AGENTS.md` now requires that rationale so a new or changed arm cannot silently reintroduce the hang. No user-visible output change. (AILAB-583 — `crates/dreamd-cli/src/cli.rs`, `AGENTS.md`)
- **The State-Drift benchmark is now the WasTrue benchmark.** The Oct-2026 third-party eval scaffold was renamed throughout: `scripts/benchmark/state_drift_bench.py` → `wastrue_bench.py`, along with its `--demo` / `--verify-determinism` / `--bakeoff` command references, the benchmark README, and the root README's roadmap row and methodology section. Repository tooling and documentation only — nothing in the shipped `dreamd` binary or the `dreamd-mcp` package changes. (AILAB-593 — `scripts/benchmark/`, `README.md`)

### Fixed

- **`uninstall` / `update` no longer stop other homes' (or other users') dreamd servers.** Both commands stopped local servers by shelling out to the manual README recipe's bare `pkill -f 'dreamd mcp'` / `pkill -f 'dreamd watch'`, which is machine-global by construction: it SIGTERMs every process on the box whose command line matches, whatever `$HOME` it serves. The 2026-08-03 clean-box audit caught it (AILAB-554 F1) — a sandboxed `HOME=/tmp/… dreamd update` killed the developer's real Cursor `dreamd mcp`. The stop pass now enumerates the process table itself, keeps only entries that are the `dreamd` binary with a matching command line, and **attributes** each one to this invocation's scope before signalling: its executable must live under this `$HOME`'s `~/.cache/dreamd-mcp`, or its own `HOME=` must resolve to this `$HOME`. Everything else is left running, named on stderr, and reported to the caller so the restart contract cannot claim "no processes were running" about a daemon that is still up. Attribution data that cannot be read (another user's `/proc/<pid>/environ` is EACCES) fails closed — failing to stop a daemon costs one command, killing someone else's does not. An empty `HOME` is now treated as no home at all, since `$HOME/.cache/dreamd-mcp` would otherwise collapse to a cwd-relative path that attributes foreign processes (and, in `uninstall`, a cwd-relative `./.npm/_npx` the scoped cache clear would *delete*). Covered by unit tests over a synthetic `/proc` tree, a cross-`$HOME` integration suite that spares and then stops a really-running `dreamd watch`, and a live step in the install-funnel suite. The `packages/dreamd-mcp` manual recipe no longer teaches the unscoped kill. (AILAB-584 — `crates/dreamd-cli/src/commands/lifecycle_cleanup.rs`, `cli.rs`, `uninstall.rs`, `update.rs`, `packages/dreamd-mcp/README.md`, `scripts/alpha/install-funnel-suite.sh`)
- **`uninstall` / `update` no longer unlink a live daemon's socket.** Both commands run a best-effort `pkill` stop pass whose failure is only a stderr warning, so on a box without `pkill` — or where the signal is denied — the daemon was still serving when its socket file was removed. That orphaned it: the daemon kept working while every client resolved a path that no longer existed, so MCP silently fell back to the in-process Phase 1 backend and cross-harness recall stopped with no error. `remove_socket` now connect-probes first and leaves a live socket in place with an actionable warning, matching the rule `dreamd archive` and `dreamd doctor --repair` already apply. Because `pkill` returns when the signal is *delivered* rather than when the target exits — and `dreamd watch` drains its coordinator and Tantivy indexer before unlinking its own socket — the probe waits out a 5s grace window first, so a daemon that is merely mid-shutdown is not mistaken for one that refused to stop. (`crates/dreamd-cli/src/commands/lifecycle_cleanup.rs`, `uninstall.rs`, `update.rs`)
- **A healthy index is no longer wiped by a false schema-mismatch match.** `is_schema_incompatible` gates a `remove_dir_all` of the index cache but matched a bare `"schema"` substring anywhere in the error text. `tantivy_io_to_index` embeds the *directory path* in its message, so any store living under a path containing "schema" (e.g. `~/dev/schema-tools/`) tripped the branch and silently rebuilt a healthy index. It now matches tantivy's exact `SchemaError` rendering (`"Schema error: '…'"`). The companion `|| msg.contains("incompatible")` alternative was removed: `TantivyError::IncompatibleIndex` renders through `Incompatibility`'s hand-written `Debug` as `"Library version: N, index version: M. …"`, so it never matched that variant and only widened the false-positive surface — an index-*format* mismatch stays a loud startup error rather than a silent wipe. (`crates/dreamd-core/src/server/tantivy_handle.rs`)

## [0.1.0-rc.8] - 2026-08-03

### Added

- **`dreamd setup` front door.** One command scaffolds `.agent/` (via `init`) and wires the harness MCP config — `.mcp.json` for Claude Code, `.cursor/mcp.json` for Cursor — with the floating `npx -y dreamd-mcp` pin. Re-running is a no-op. `--harness claude|cursor|both` selects which configs are written. (`crates/dreamd-cli`)
- **TTY interactive wizard for `setup`.** Without `--yes`, `setup` prompts interactively for harness choice and confirmation; off a TTY it fails fast with exit 2 rather than blocking (AILAB-551).
- **`setup --force` + MCP-conflict handling (AILAB-548).** A hard-pinned `dreamd-mcp@…` block, a local `command: "dreamd"` build, and unreadable JSON all refuse with exit 1 (no write); `--force` overrides only the pin case, preserving every third-party server. The compatible `--project-root` form is accepted byte-identically, and `--harness both` is atomic — nothing is written if any target conflicts.
- **`update --restart` flag.** Explicitly stops a running daemon after clearing the cache; `update --dry-run` prints the restart contract without touching anything (AILAB-552).
- **Install-funnel CI gate.** Sandboxed end-to-end suite covering cold `setup`, `doctor`, idempotence, `update --dry-run`, and the full AILAB-548 conflict taxonomy (`scripts/alpha/install-funnel-suite.sh`).

## [0.1.0-rc.7] - 2026-07-23

### Fixed

- **`tracing::warn!` demoted to `tracing::info!` for absent index manifest.** First-run users saw a scary `WARN` log message ("no index manifest found; treating project as unindexed") on every fresh project. This is the expected first-run state — now logged at `INFO`. (`crates/dreamd-core/src/server/lifecycle.rs:133`)
- **`eprintln!` demoted to `tracing::debug!` for MCP daemon-not-found fallback.** The Phase 1 in-process fallback message ("daemon not found — running in-process") was printed to stderr as plain text, confusing first-time users who thought the daemon had failed. Now only visible with `DREAMD_LOG=debug`. (`crates/dreamd-core/src/mcp/mod.rs:583`)
- **`[dreamd-mcp] Fatal error:` prefix reserved for actual shim crashes.** The JS shim's top-level catch handler printed `Fatal error:` for every error including expected CLI errors from the child process (e.g. "no project root found"). CLI errors (non-zero exit from `execFileSync`) now write `[dreamd-mcp] command exited with code N` without the scary prefix. Actual shim crashes (sha256 mismatch, network failure, signal kill) keep the `Fatal error:` prefix. (`packages/dreamd-mcp/bin/dreamd-mcp.js:334-342`)
- **`memchr` lockfile bumped v2.8.0 → v2.8.3.** Avoids nightly-toolchain ICE on Windows caused by 2024-edition prelude changes in older patch versions. (`Cargo.lock`)

## [0.1.0-rc.6] - 2026-07-22

### Fixed

- **`skill_action` docs advertised a format the validator rejects.** The MCP `append_node` tool schema doc, the `server.instructions` agent guide, and the `adapters/claude-code/AGENTS.md.snippet` copy-in all told clients the clustering key allowed `[a-z0-9_:.-]` with dots as separators (e.g. `rust.async.tokio`), but the ingress validator (`SkillAction::parse`) accepts only lowercase `[a-z0-9_]` segments joined by `::` and rejects dots, hyphens, and slashes with `invalid skill_action`. Agents that followed the docs produced rejected writes. All three now describe the real format (`rust::async::tokio`). Docs-only change — the validator is unchanged; the rc.4 ANTH-150/151 guidance was the source of the mismatch. (The other doc surfaces — `SKILL.md`, `llms-full.txt`, `docs/http-api.md`, `docs/adapters.md`, `docs/glossary.md`, `AGENTS.md`, and the cursor/aider/cline adapters — already documented the correct `::` form.)

## [0.1.0-rc.5] - 2026-07-22

### Fixed

- **`dreamd-mcp` npx shim ran the wrong binary.** The published `0.1.0-rc.4` package silently downloaded and ran the **rc.3** native binary: a hardcoded `VERSION` constant in `bin/dreamd-mcp.js` drove the release-download URL and per-version cache path while `package.json` / `manifest.json` advertised rc.4. `VERSION` is now derived from `package.json`, so the release tag (`v${VERSION}`), download URL, cache dir, and `--version` output can never drift from the package version again.
- Corrected the bundled `manifest.json` binary `sha256` digests, which had drifted a release behind the version field (a `VERSION` bump alone would otherwise have failed sha256 verification at runtime).
- Restored a green CI baseline: the `test` job is gated on `lint`, so a formatting violation had silently masked a stale `Cargo.lock` and stale `dreamd --version` snapshots. All corrected.

### Added

- Version-consistency guard test for the shim (`-V` / `--version` must equal `package.json`), and a CI job that runs the shim's `node --test` suite (previously ungated — the reason the broken package shipped).
- `dreamd-mcp` README: pin-`@latest` guidance (a bare `npx dreamd-mcp` caches the first resolved version and never re-checks the registry) and a true uninstall / reset procedure.
- `RELEASING.md` — the canonical, drift-proof release procedure.

### Changed

- Locked in `dreamd mcp` clean-shutdown-on-stdin-EOF with regression tests (`crates/dreamd-cli/tests/mcp_stdin_eof.rs`): a normal MCP disconnect exits 0; a pre-initialize disconnect exits non-zero but still terminates promptly (no orphaned process).

## [0.1.0-rc.4] - 2026-07-21

### Added

- `dreamd migrate --from <ver> --to <ver>` — episodic schema migration command (WEG-133 / DR-108). v0.1 ships a stub: the only registered path is the identity `1.0.0 → 1.0.0` (a no-op success), backed by a `dreamd-core::migrate` trait + registry so v0.1.1 can plug in real transforms. `--from`/`--to` are episodic record schema strings (`RECORD_SCHEMA_VERSION`), distinct from the daemon `state.json` schema and the Tantivy index schema. On the no-op path it copies present durable files (`AGENT_LEARNINGS.jsonl`, `state.json`) to sibling `.bak` files; the self-healing index is never rewritten or backed up. Documented in `docs/migrate.md`.
- Documented HTTP API stability policy: `/api/v1/*` is **not** a stable interface in v0.1. Breaking changes to request shapes, response shapes, and status codes may land between v0.1.x releases, each called out here; stabilization is intended at v0.2. The on-disk `.agent/` contract is governed separately and remains frozen for v0.1 (see `SPEC.md`). Full rationale in `docs/architecture.md` § API stability (WEG-90 / DR-904).
- Root `Justfile` with `dev` / `test` / `bench` / `release` / `lint` recipes wrapping the canonical cargo invocations for common contributor loops; documented in `CONTRIBUTING.md`. Contributor convenience only — CI still calls cargo directly (WEG-33 / DR-005).
- MCP `initialize` response now includes a structured agent usage guide in `server.instructions`: session discipline (search at start, append at close), `skill_action` charset rules (`[a-z0-9_:.-]`, dots only), importance/pain scoring, `client_dedup_key` pattern, and what not to store. Fixed `AppendNodeParams.skill_action` doc comment to show a valid dot-separated example. Expanded `adapters/claude-code/AGENTS.md.snippet` with the same guide in Markdown form (ANTH-150, ANTH-151).

## [0.1.0-rc.3] - 2026-07-13

### Added

- `dreamd archive --force-unpin` — operator safety valve that clears sticky `pinned` flags on episodic entries via an atomic rewrite, guarded by a daemon-live refusal check (WEG-134 / DR-116).
- Recall responses now surface provenance anchors under `metadata` — `skill_action` (cluster key) and `source_harness` (authoring harness) — so recall is cross-harness-attributable (WEG-424).
- Self-healing index rebuild on schema-version mismatch: `TantivyIndexHandle::open` wipes and replays the JSONL under the current schema when an on-disk index predates the binary, on both the daemon and no-daemon paths (WEG-424).

### Changed

- Learn responses (`POST /api/v1/learn` and MCP `append_node`) now return a daemon-minted `timestamp` from the coordinator, matching the `EventId` overwrite rule; client-supplied timestamps in the request body are ignored on success.
- Tantivy index schema bumped `index/1.2` → `index/1.3` (adds the `skill_action` + `source_harness` STORED fields). Existing indexes rebuild automatically from the JSONL on first open.

## [0.1.0-rc.1] - 2026-06-22

### Added

- `dreamd watch` — foreground daemon mode (Unix; SIGINT/SIGTERM-graceful shutdown).
- `dreamd dream` — deterministic dream cycle CLI (`--auto` hidden flag; deterministic-only path always available without network). `--dry` preview is planned for v0.1.1.
- `dreamd reset workspace` — re-scaffolds `working/WORKSPACE.md` to its initial state.
- `dreamd version` — structured version output block with build metadata.
- `dreamd doctor` — health-check output (dream-cycle mode and state-surface diagnostics).
- `dreamd init --uninstall-project` — removes the current project entry from the global registry.
- `--quiet` flag on `dreamd init` to suppress non-essential output.
- HTTP API on Unix domain socket: `POST /api/v1/learn`, `GET /api/v1/recall`, `POST /api/v1/dream`, `GET /api/v1/preferences`.
- MCP server (`dreamd mcp`) — `search_nodes` and `append_node` tools; Phase 1 in-process / Phase 2 UDS bridge.
- `SO_PEERCRED` peer-credential middleware on the UDS API (UID-match enforcement on Linux/macOS).
- `X-Agent-Root` header routing and per-user project registry at `~/.agent/registry.toml`; `dreamd init` registers each project automatically.
- Tantivy 0.26 full-text index with 5-second commit cadence; salience-aware recall collector (BM25 × exponential-decay × pain × importance × log-scaled recurrence).
- Episodic decay: events with score < 2.0 and age > 90 days are archived to `.dreamd/snapshots/YYYY-MM-DD.jsonl`, never deleted.
- Dream-cycle WAL at `.dreamd/dream_in_progress.wal`; startup recovers torn cycles before serving traffic.
- Recurrence sidecar at `semantic/recurrence_counts.json`; per-`skill_action` cluster counts drive promotion and the salience formula.
- Privacy disclosure printed on first run in any directory without an existing `.agent/` store.
- `npx dreamd-mcp` Node.js shim for zero-install MCP server distribution.
- Agent output redaction: high-entropy strings matching common token patterns are stripped from `content` before append on every path — the HTTP `POST /api/v1/learn` endpoint and the MCP `append_node` tool, both Phase 1 (in-process) and Phase 2 (daemon bridge).
- Criterion benchmark suite for recall latency (`cargo bench -p dreamd-core`).
- `rmcp 1.7.0` (MCP spec 2025-11-25) added as workspace dependency; consumed by `dreamd mcp` subcommand.
- GitHub Actions CI/CD pipeline: lint, test, cross-platform build, binary size gate (NFR-2), DCO sign-off check.
- Release workflow: cross-platform binary builds published to GitHub Releases on tag push.
- Initial project scaffold (Cargo workspace, `SPEC.md`, `CONTRIBUTING.md`, `SECURITY.md`, `CODE_OF_CONDUCT.md`).
- Per-project coordinator routing: each project's `.agent/` store gets its own isolated writer, so memory from one repo can't be misfiled into another.
- `--project-root` flag on `dreamd mcp`, letting IDE adapters pin the project store explicitly (fixes the agent-root mismatch seen in Cursor/Cline).

### Changed

- `AgentLearning.id` is now `EventId` (daemon-minted `evt_`-prefixed Crockford base32 ULID); clients no longer supply IDs — any inbound `id` is overwritten by the coordinator.
- Topology: `npx dreamd-mcp` auto-detects a running daemon and bridges over UDS (Phase 2); otherwise it runs an in-process server (Phase 1). `dreamd watch` provides the shared serialized writer for multi-agent setups.
- `skill_action` keys are normalized and validated to `[a-z0-9_]` segments joined by `::` (e.g. `rust::borrow_checker`); previously-tolerated `.` and `-` are now rejected.
- `dreamd dream` proxies to the running daemon over the Unix domain socket when one is live (running in-process only when no daemon is reachable), so a manual cycle can't race the daemon's writer.

### Fixed

- Dream cycle no longer orphans the coordinator's append file descriptor after the atomic `LESSONS.md`/JSONL renames; appends written during a cycle could previously be dropped.
- `npx dreamd-mcp <subcommand>` routing corrected.
- `dreamd watch` unlinks its Unix domain socket on `SIGTERM`, so a clean restart no longer trips over a stale socket.
- `dreamd init` refuses to scaffold a phantom `.agent/` store when no project-root sentinel is present, instead of leaving an orphan.
- macOS Unix-socket `sun_path` overflow when `$TMPDIR` is long.

### Security

- `~/.agent/` is created atomically at mode `0700` and `registry.toml` is stamped `0600`, closing the brief world-readable window during directory creation.
- `schema_version` is now server-stamped on the raw `POST /api/v1/learn` path (previously client-trusted).
